Módulo 01 · Aula 1.1

A lógica de nodes e cenas

Entender a estrutura fundamental do Godot antes de escrever uma linha de código. O maior choque de quem chega do zero numa engine.

~30 minutos Conceitual

O que é um node?

Se você já trabalhou com POO, sua intuição inicial vai ser: "node é uma classe, cena é um objeto". Isso está parcialmente certo — mas na prática o Godot inverte o que você está acostumado a fazer.

Em linguagens tradicionais, você escreve uma classe Player que herda de Character, instancia ela no main() e chama métodos. No Godot, você não escreve um main(). Você monta uma árvore de nodes — e a engine executa essa árvore pra você.

Analogia

Pense num node como um bloco LEGO especializado. Cada tipo de node já tem um comportamento embutido: um Sprite2D sabe como desenhar uma textura, um CollisionShape2D sabe como ocupar espaço físico, um AudioStreamPlayer sabe como tocar áudio. Você combina blocos, não reimplementa tudo do zero.

A árvore de cenas

Nodes se organizam em hierarquia pai → filho. Essa hierarquia é a SceneTree — a estrutura central que a engine lê a cada frame. Quando um node pai se move, todos os filhos acompanham. Quando o pai é removido, os filhos vão junto.

Exemplo: cena de um inimigo patrulheiro
Enemy [CharacterBody2D] ← Enemy.cs ├── Sprite2D [Sprite2D] ├── CollisionShape2D [CollisionShape2D] ├── DetectionArea [Area2D] │ └── CollisionShape2D [CollisionShape2D] └── PatrolRayCast [RayCast2D]

Cada node dessa árvore é responsável por uma coisa só. Você não escreve código de detecção dentro do script de movimento — você adiciona um node Area2D que já sabe fazer isso, e reage ao que ele emite.

Classe vs. instância vs. cena

No Godot, uma cena é um arquivo .tscn que descreve uma árvore de nodes com suas propriedades configuradas. É como um prefab: uma cena de Coin pode ser instanciada dezenas de vezes no mapa. Cada instância é independente, mas todas partem do mesmo template.

OOP tradicional
  • Você define class Player
  • Herança para reutilizar comportamento
  • Você instancia no main()
  • Comunicação por chamada direta de método
Godot (nodes)
  • Você cria uma cena com nodes
  • Composição de nodes para reutilizar
  • Engine instancia via SceneTree
  • Comunicação preferencialmente por signals
Para quem vem de Unity

A diferença principal: no Unity, um GameObject é quase vazio e você adiciona Components. No Godot, cada node já é um tipo específico com comportamento. A hierarquia de herança fica mais simples, e a composição fica mais explícita na SceneTree.

Scripts são anexados a nodes

Um script C# no Godot não é uma classe independente que você instancia manualmente. Ele é anexado a um node e estende o comportamento desse node. Quando o engine processa aquele node, ele executa seu script automaticamente.

Player.cs C# 
using Godot;

// Este script estende CharacterBody2D —
// ele só pode ser anexado a um node desse tipo.
public partial class Player : CharacterBody2D
{
    // [Export] expõe a variável no Inspector do editor
    [Export] public float Speed = 200f;

    // Chamado uma vez quando o node entra na SceneTree
    public override void _Ready()
    {
        GD.Print("Player pronto!");
    }

    // Chamado a cada frame de física (~60x por segundo)
    public override void _PhysicsProcess(double delta)
    {
        // Lógica de movimento aqui
    }
}

Repare que você não instancia Player manualmente. Você anexa esse script ao node Player na cena, e a engine cuida do ciclo de vida.

Ponto-chave

O método _Ready() é o seu "construtor seguro" — quando ele é chamado, todos os filhos do node já existem e podem ser acessados. Já o construtor padrão do C# (Player()) é chamado antes disso e não deve ser usado para lógica de jogo.

O loop principal: o que acontece a cada frame

Até aqui você viu a estrutura — nodes, cenas, scripts. Mas o que faz isso rodar é a engine repetindo um ciclo várias vezes por segundo, o game loop. Entender a ordem desse ciclo evita boa parte dos bugs de inicialização e de timing que você vai encontrar mais adiante.

Do F5 ao primeiro frame
1
Godot carrega a cena principal

Lê o project.godot, encontra a cena marcada como principal e instancia toda a árvore de nodes descrita nela.

2
_EnterTree() — de cima para baixo

Conforme cada node é adicionado à SceneTree, ele recebe esse callback. O pai entra primeiro, depois os filhos, na ordem em que aparecem na árvore.

3
_Ready() — de baixo para cima

Na ordem inversa do passo anterior: um node só recebe _Ready() depois que todos os seus filhos já receberam o deles. É por isso que GetNode() dentro de _Ready() é seguro.

4
Loop principal — repete a cada frame

A partir daqui a engine entra em loop: processa input, roda física, roda a lógica de jogo e desenha a tela. Esse ciclo só para quando o jogo é fechado.

Dentro de cada volta do loop, dois callbacks competem por atenção — e a diferença entre eles é uma das maiores fontes de bugs em quem está começando:

_PhysicsProcess(delta)
  • Taxa fixa: 60 vezes por segundo por padrão
  • delta é sempre o mesmo valor (≈0.0166s)
  • Pode rodar 0, 1 ou várias vezes por frame renderizado
  • Use para: movimento, colisão, física
_Process(delta)
  • Roda exatamente uma vez por frame renderizado
  • delta varia com a taxa de quadros atual
  • Não é sincronizado com a física
  • Use para: animação, UI, lógica que não depende de física
Por que multiplicar por delta?

Sem delta, o código Position += new Vector2(Speed, 0) move o personagem Speed pixels por frame. Em uma máquina rodando a 120 FPS ele anda o dobro do que em outra rodando a 60 FPS — o jogo fica mais rápido em hardware melhor. Multiplicando por delta você define a velocidade em pixels por segundo: a engine escala automaticamente para quantos frames aconteceram naquele intervalo. Em _PhysicsProcess o delta é quase constante (taxa fixa), mas em _Process é essencial para comportamento consistente entre máquinas.

Onde os signals entram nisso

Signals não são uma fila separada: EmitSignal() chama os métodos conectados imediatamente, na mesma execução, antes de continuar o resto da função que emitiu. Se o Player emite um signal dentro de _PhysicsProcess(), quem está ouvindo já roda ainda dentro daquele mesmo frame de física.

E quando um node é removido?

Chamar Free() no meio de um _PhysicsProcess() pode quebrar a iteração da engine sobre a árvore. Por isso o padrão é QueueFree(): marca o node para ser removido com segurança no fim do frame atual, em vez de destruí-lo instantaneamente.

Signals: o padrão Observer nativo

O mecanismo de comunicação entre nodes do Godot — e por que ele existe em vez de chamadas diretas de método.

~35 minutos Código + editor

Por que não chamar métodos diretamente?

Imagine que seu Player precisa avisar a HUD quando perde uma vida. A abordagem mais óbvia seria:

Player.cs — abordagem problemática C# 
// Player precisa "conhecer" a HUD — acoplamento forte
var hud = GetNode<HUD>("/root/Level/UI/HUD");
hud.UpdateLives(lives);

Isso funciona, mas cria um problema: o Player agora depende da estrutura exata da cena. Se você mover a HUD de lugar, renomear o nó ou criar um nível sem HUD (numa cena de teste, por exemplo), o código quebra.

Quando referência direta é aceitável: [Export]

Se o Player é pai da HUD e precisa controlá-la, a solução é expor a referência pelo Inspector. O Godot resolve o vínculo na hora de salvar a cena — nenhuma string para quebrar, nenhuma dependência de caminho:

Player.cs — com Export C# 
public partial class Player : CharacterBody2D
{
    // No Inspector, arraste o node HUD para este campo
    [Export] public HUD Hud;

    public void TakeDamage()
    {
        _lives--;
        Hud.UpdateLives(_lives); // sem string de caminho
    }
}

Mas essa abordagem ainda acopla Player ao tipo HUD. Se você quiser usar o Player numa cena de teste sem HUD, vai precisar tratar a referência nula ou remover o campo. Para comunicação de filho para pai — ou entre nodes não relacionados — existe uma solução melhor.

A regra de ouro da arquitetura Godot

Chame para baixo, sinalize para cima. Um pai pode acessar seus filhos diretamente — com GetNode() ou [Export]. Um filho nunca deve acessar o pai ou irmãos diretamente: ele emite um signal e quem quiser reagir se conecta. Isso mantém cada cena funcional independentemente de onde for instanciada.

Analogia com padrão Observer

Signals são exatamente o padrão Observer que você já conhece — só que embutido na engine. O emitente não conhece os ouvintes. Quem quer saber de um evento se registra para ouvir; quem emite só dispara o sinal sem se preocupar com quem está escutando.

Signals embutidos vs. signals customizados

Todo node já vem com signals prontos. Um Button emite pressed. Um Area2D emite body_entered. Você também pode declarar seus próprios signals em C#:

Player.cs C# 
using Godot;

public partial class Player : CharacterBody2D
{
    // Declara um signal que passa o número de vidas restantes
    [Signal] public delegate void LifeLostEventHandler(int livesRemaining);

    private int _lives = 3;

    public void TakeDamage()
    {
        _lives--;

        // Emite o signal — quem estiver ouvindo recebe
        EmitSignal(SignalName.LifeLost, _lives);

        if (_lives <= 0)
            Die();
    }
}
Convenção do Godot 4 em C#

O atributo [Signal] sobre um delegate void com sufixo EventHandler é a forma canônica no Godot 4 com C#. O Godot gera automaticamente o nome LifeLost (sem o sufixo) para usar em EmitSignal e Connect.

Conectando signals: editor vs. código

Há duas formas de conectar um signal a um método receptor. Cada uma tem seu lugar:

Via editor (drag-and-drop)

Selecione o node emissor na SceneTree → aba Node (ao lado de Inspector) → Signals → dê duplo-clique no signal → selecione o node receptor → nomeie o método → Conectar. O Godot cria o método no script automaticamente.

Scene
▾ Level
  Player
  UI

Use o editor quando
  • A conexão é estática (nunca muda em runtime)
  • Os dois nodes existem na mesma cena
  • É uma conexão simples, de um para um
  • Prototipando rápido
Use código quando
  • O receptor é instanciado dinamicamente
  • A conexão depende de lógica de runtime
  • Você quer Callable com parâmetros extras
  • O emissor é de outra cena

Via código

Level01.cs — conectando por código C# 
public partial class Level01 : Node2D
{
    public override void _Ready()
    {
        var player = GetNode<Player>("Player");
        var hud    = GetNode<HUD>("UI/HUD");

        // Conecta: quando Player emitir LifeLost,
        // chama hud.OnLifeLost(livesRemaining)
        player.LifeLost += hud.OnLifeLost;
    }
}
HUD.cs — método receptor C# 
public partial class HUD : CanvasLayer
{
    // A assinatura deve bater com o delegate do signal
    public void OnLifeLost(int livesRemaining)
    {
        GetNode<Label>("LivesLabel").Text = $"Vidas: {livesRemaining}";
    }
}

Repare que o Player não importa, não referencia e não conhece a classe HUD. Ele só emite. Quem conecta é o Level01 — o node pai que tem visibilidade de ambos.

Padrão recomendado

Nodes filhos não devem referenciar o pai — isso cria dependência circular. O pai (ou um gerenciador) conhece os filhos e faz a ponte via signals. Signals de filho para cima (filho → pai) são naturais; chamadas de filho para filho atravessando o pai são sinal de que o design precisa de signals.

Grupos: comunicação um para muitos

Signals conectam um emissor a receptores específicos. Mas e quando você precisa chamar um método em todos os inimigos ao mesmo tempo, sem manter uma lista de referências? Para isso existe o sistema de grupos — uma tag aplicada a nodes que permite acioná-los em conjunto:

Enemy.cs — entrar no grupo C# 
public override void _Ready()
{
    AddToGroup("enemies");
}

public void Explode()
{
    // lógica de explosão
    QueueFree();
}
SmartBomb.cs — chamar todos do grupo C# 
public void Detonate()
{
    // Chama Explode() em todos os nodes com a tag "enemies"
    GetTree().CallGroup("enemies", "Explode");
}

Você também pode adicionar nodes a grupos pelo editor: selecione o node → aba Node → Groups. Grupos definidos pelo editor ficam salvos no .tscn e persistem entre sessões. Veja CallGroup() e AddToGroup() na documentação para variantes e opções disponíveis.

Grupos vs. signals

Signals avisam quem se registrou para ouvir — ótimo para relações de um para um ou poucos receptores conhecidos. Grupos chamam todos os nodes de uma categoria sem referências individuais — ótimo para sistemas de broadcast como dano em área, pausa geral, ou troca de fase. Em projetos reais você vai usar os dois.

Signals na prática: botão que conta cliques

Exercício simples mas que cobre o ciclo completo: node emissor → signal → node receptor → atualização de UI.

1
Monte a cena

Crie uma nova cena com Node2D como raiz. Adicione filhos: Button e Label. Posicione-os no viewport com a ferramenta de mover.

2
Conecte o signal pelo editor

Selecione o Button → aba Node → signal pressed → duplo clique → selecione o Node2D raiz como receptor → método sugerido: _on_button_pressed → Conectar.

3
Implemente o método gerado

O editor cria o método no script do Node2D. Adicione uma variável de contagem e atualize o texto do Label a cada clique.

4
Crie e emita um signal customizado

Declare um signal [Signal] public delegate void CountReachedEventHandler(int count); no Node2D. Emita-o quando a contagem atingir 5. Conecte por código a um método que muda a cor do Label.

SignalDemo.cs C# 
using Godot;

public partial class SignalDemo : Node2D
{
    [Signal] public delegate void CountReachedEventHandler(int count);

    private int _count = 0;
    private Label _label;

    public override void _Ready()
    {
        _label = GetNode<Label>("Label");
        // Conecta o signal customizado por código (lambda)
        CountReached += count =>
            _label.Modulate = count >= 5 ? Colors.Green : Colors.White;
    }

    // Gerado pelo editor ao conectar Button.pressed
    private void _on_button_pressed()
    {
        _count++;
        _label.Text = $"Cliques: {_count}";
        if (_count == 5)
            EmitSignal(SignalName.CountReached, _count);
    }
}
Observe

Quando a conexão do editor e a conexão por código coexistem, o signal pode ter vários ouvintes. Um signal pode ser conectado a quantos métodos quiser — todos são chamados na ordem de conexão. Isso é uma das forças do padrão Observer.

Placar desacoplado Aula 1.3 — Signals
Intermediário

Implemente um mini-sistema de placar usando signals, onde nenhuma das cenas conhece a outra diretamente. Você decide a estrutura — o requisito é o desacoplamento.

Contexto

Você tem três cenas independentes: um Enemy que pode morrer, um Scoreboard que exibe pontos, e um Level que as instancia. A regra: o script de Enemy não pode ter nenhuma referência à classe Scoreboard, e vice-versa.

Objetivos

  • 1
    Cena Enemy.tscn com um script que declara um signal Died e o emite quando uma tecla (ex: K) é pressionada — simula o inimigo sendo morto
  • 2
    Cena Scoreboard.tscn com um Label que exibe a pontuação e um método público que recebe quantos pontos adicionar
  • 3
    Cena Level.tscn que instancia ambos e conecta o signal Died do Enemy ao método do Scoreboard — sem que Enemy ou Scoreboard saibam um do outro
  • 4
    Instanciar 3 inimigos diferentes no Level, cada um com um valor de pontos diferente via [Export]. Matar cada um deve adicionar a pontuação correta ao placar
Critério de aprovação

Abra o script de Enemy.cs e verifique: há alguma menção à palavra "Scoreboard"? Se sim, o desafio não foi concluído. O mesmo vale para Scoreboard.cs — não pode ter referência a "Enemy". A ponte existe só no Level.cs.

O signal Died precisa passar o valor de pontos: [Signal] public delegate void DiedEventHandler(int points);. O inimigo não sabe quem vai receber — ele só emite o valor.

No Level.cs, após pegar as referências com GetNode, a conexão fica: enemy.Died += scoreboard.AddPoints;. O método AddPoints no Scoreboard recebe um int e atualiza o Label.
