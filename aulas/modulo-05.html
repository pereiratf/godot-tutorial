Módulo 05 · Aula 5.1

HUD com CanvasLayer

Mostrar pontuação e vidas na tela — uma interface que fica fixa enquanto o mundo se move — e centralizar o estado do jogo num autoload.

~30 minutos C# + UI

O problema: a UI não pode andar com o mundo

No Módulo 04 o player coleta gemas e toma dano — mas nada disso aparece na tela. Precisamos de um HUD (Heads-Up Display): pontuação, vidas, informação sempre visível. E aqui surge um problema: se você colocar um Label na cena do mundo, ele fica preso a uma posição do mundo e some quando a câmera se move.

A UI precisa viver num espaço diferente — o espaço da tela, fixo, indiferente à Camera2D. No Godot esse espaço é o CanvasLayer.

O vidro do para-brisa

Imagine dirigir: a paisagem passa pela janela, mas o velocímetro colado no vidro fica parado no seu campo de visão. O CanvasLayer é esse vidro — tudo dentro dele é desenhado por cima do jogo, fixo na tela, enquanto o mundo rola atrás.

CanvasLayer + Control: a caixa de ferramentas de UI

Dentro do CanvasLayer você usa os nodes de UI, que herdam de Control — diferentes dos Node2D do gameplay. Em vez de posição livre, os Control usam âncoras: você prende um elemento a um canto da tela e ele fica lá em qualquer resolução.

Node2D (gameplay)
  • Vive no espaço do mundo
  • Posição em pixels do nível
  • Se move com a câmera
  • Player, inimigos, gemas
Control (UI)
  • Vive no espaço da tela
  • Posição por âncoras/margens
  • Fixo, ignora a câmera
  • Labels, botões, barras de vida
Estrutura do HUD na cena do mundo
World ├── Ground (TileMapLayer) ├── Player (CharacterBody2D) └── HUD (CanvasLayer) Hud.cs ├── ScoreLabel (Label) ancorado no topo-esquerda └── LivesLabel (Label) ancorado no topo-direita

Onde mora o placar? O autoload

Aqui está a decisão de arquitetura mais importante do módulo. A Gem quer somar pontos; o HUD quer mostrar pontos; o Player quer perder vidas. Se cada um guardar seu próprio número, eles se desencontram. E quando você troca de cena (game over, próxima fase), tudo se perde.

A solução do Godot é o autoload (singleton): um node registrado em Project Settings → Autoload que o Godot cria automaticamente e mantém vivo acima de todas as cenas. Ele existe antes do nível carregar e sobrevive a trocas de cena. É o lugar natural para o estado do jogo: pontuação, vidas, fase atual.

Singleton, sem drama

"Singleton" assusta, mas a ideia é simples: uma instância global que todo mundo enxerga. O GameManager vira acessível de qualquer script por GameManager.Instance, sem precisar de referências passadas de node em node.

Signals: o GameManager avisa, o HUD reage

Para não acoplar o HUD ao resto, usamos signals (como nos módulos anteriores). O GameManager emite ScoreChanged quando o placar muda; o HUD escuta e atualiza o Label. Nenhum dos dois precisa conhecer o outro diretamente.

GameManager.cs — autoload C# 
using Godot;

public partial class GameManager : Node
{
    // Acesso global: GameManager.Instance.AddScore(1)
    public static GameManager Instance { get; private set; }

    [Signal] public delegate void ScoreChangedEventHandler(int score);
    [Signal] public delegate void LivesChangedEventHandler(int lives);

    public int Score { get; private set; }
    public int Lives { get; private set; } = 3;

    public override void _Ready() => Instance = this;

    public void AddScore(int amount)
    {
        Score += amount;
        EmitSignal(SignalName.ScoreChanged, Score);
    }

    public void LoseLife()
    {
        Lives--;
        EmitSignal(SignalName.LivesChanged, Lives);
    }
}
Hud.cs C# 
using Godot;

public partial class Hud : CanvasLayer
{
    private Label _scoreLabel;
    private Label _livesLabel;

    public override void _Ready()
    {
        _scoreLabel = GetNode<Label>("ScoreLabel");
        _livesLabel = GetNode<Label>("LivesLabel");

        // Escuta o GameManager e já sincroniza o valor inicial
        GameManager.Instance.ScoreChanged += OnScoreChanged;
        GameManager.Instance.LivesChanged += OnLivesChanged;
        OnScoreChanged(GameManager.Instance.Score);
        OnLivesChanged(GameManager.Instance.Lives);
    }

    private void OnScoreChanged(int score) => _scoreLabel.Text = $"Gemas: {score}";
    private void OnLivesChanged(int lives) => _livesLabel.Text = $"Vidas: {lives}";
}

E o gancho que ficou pendente no Módulo 04 finalmente fecha: dentro da Gem, ao coletar, basta chamar GameManager.Instance.AddScore(1) antes do QueueFree().

Montar o HUD e o placar

Vamos criar o autoload do estado do jogo, um HUD fixo na tela e ligar a coleta de gemas ao placar.

Projeto base deste módulo

Continue do projeto do Módulo 04 (com Gem, Enemy e o Player tomando dano). Se preferir, baixe o projeto base atualizado.

1
Crie o GameManager

Crie GameManager.cs (código da aba Conteúdo) herdando de Node. Não precisa de cena: em Project Settings → Autoload, aponte para o script, dê o nome de node GameManager e clique em Add.

2
Adicione o CanvasLayer

Abra mapa_1.tscn. Na raiz, adicione um CanvasLayer renomeado para HUD. Tudo dentro dele fica fixo na tela.

3
Adicione os Labels

Dentro do HUD, adicione dois Label: ScoreLabel e LivesLabel. Use os anchor presets (barra superior do editor 2D) para ancorar um no topo-esquerda e outro no topo-direita. Dê um tamanho de fonte legível no Inspector (Theme Overrides → Font Sizes).

4
Anexe o Hud.cs

Anexe Hud.cs ao node HUD. Ele busca os dois labels e se inscreve nos signals do GameManager.

5
Ligue a coleta ao placar

No Gem.cs, dentro do OnBodyEntered (antes do QueueFree()), adicione GameManager.Instance.AddScore(1);. Cada gema agora soma 1 ponto.

6
Teste

Pressione F5. Ande pelo nível e colete gemas — o ScoreLabel deve subir na hora. Mova a câmera andando: o HUD permanece fixo na tela.

Ordem do autoload importa

O _Ready do Hud usa GameManager.Instance. Como o autoload é criado antes das cenas, o Instance já existe quando o HUD carrega. Se der null, confirme que o GameManager está mesmo registrado em Autoload (e não só como um script solto).

Vidas em corações, não em número Aula 5.1 · Control + TextureRect
Médio

Um número de vidas é funcional, mas corações comunicam na hora. Troque o LivesLabel por uma fileira de ícones que some um coração a cada dano.

  • 1
    Substitua o LivesLabel por um HBoxContainer chamado LivesBox
  • 2
    Preencha com TextureRect usando um sprite de coração (ou a própria gema/cereja do Sunny Land)
  • 3
    No OnLivesChanged, mostre/esconda corações conforme o número de vidas (ajuste Visible de cada um)
  • 4
    Teste levando dano de um inimigo e confirme que um coração desaparece por vida perdida

Um HBoxContainer alinha os filhos numa linha automaticamente — não precisa posicionar coração por coração.

No OnLivesChanged(int lives), itere pelos filhos do container: GetChildren() e para cada índice i, defina coracao.Visible = i < lives;. Assim, com 2 vidas, só os 2 primeiros corações aparecem.

Módulo 05 · Aula 5.2

Game loop e transições

Fechar o ciclo do jogo: perder vidas leva ao game over, vencer leva à vitória, e cada final oferece recomeçar — com troca de cenas.

~30 minutos C# + cenas

O que é o "game loop"

Um jogo não é só um nível rodando: é um ciclo. O jogador entra, joga, e uma de duas coisas acontece — ele vence ou perde. Em qualquer caso, o jogo oferece recomeçar. Fechar esse ciclo é o que transforma o seu protótipo num jogo de verdade.

O ciclo do jogo
▶
Jogando
O nível roda; o player coleta gemas e evita inimigos
✕
Game Over
Vidas chegam a zero → tela de derrota → recomeçar
★
Vitória
Objetivo cumprido → tela de vitória → jogar de novo

Trocar de cena

Cada tela do ciclo (nível, game over, vitória) é uma cena. Passar de uma para outra é trocar a cena ativa. O Godot faz isso com dois métodos da SceneTree:

Métodos de troca de cena
ChangeSceneToFile(caminho)
Descarrega a cena atual e carrega outra pelo caminho res://.... Usado para ir ao game over, à vitória ou ao próximo nível.
ReloadCurrentScene()
Recarrega a cena atual do zero. Atalho perfeito para "tentar de novo" no mesmo nível.
O autoload sobrevive — resete-o

Trocar de cena não reinicia o GameManager: ele é autoload, vive acima das cenas. Então, ao recomeçar, as vidas ainda estão em zero e o placar acumulado. Você precisa explicitamente chamar um Reset() no GameManager ao iniciar uma nova partida. Esse é o preço (e a graça) de um estado que persiste.

Derrota: de LoseLife ao game over

Voltamos ao GameManager. Quando as vidas zeram, ele dispara a troca para a tela de game over. E adicionamos o Reset() que a nova partida vai chamar.

GameManager.cs — derrota e reset C# 
    public void LoseLife()
    {
        Lives--;
        EmitSignal(SignalName.LivesChanged, Lives);

        if (Lives <= 0)
            GetTree().ChangeSceneToFile("res://Scenes/UI/GameOver.tscn");
    }

    // Chamado ao (re)iniciar uma partida
    public void Reset()
    {
        Score = 0;
        Lives = 3;
        EmitSignal(SignalName.ScoreChanged, Score);
        EmitSignal(SignalName.LivesChanged, Lives);
    }

A tela de game over é uma cena simples: um Control com um texto e um botão. O botão conecta seu signal pressed a um método que reseta o estado e recarrega o nível.

GameOver.cs C# 
using Godot;

public partial class GameOver : Control
{
    // Conectado ao signal "pressed" do botão "Tentar de novo"
    private void OnRetryPressed()
    {
        GameManager.Instance.Reset();
        GetTree().ChangeSceneToFile("res://Scenes/World/mapa_1.tscn");
    }
}
Pausar em vez de trocar

Para um menu de pause (não um game over), em vez de trocar de cena você congela o jogo com GetTree().Paused = true e mostra um Control por cima. Para o menu continuar respondendo enquanto tudo está pausado, ajuste o Process Mode dele para Always no Inspector. Fica como leitura para depois.

Fechar o ciclo

Vamos ligar o dano do Módulo 04 às vidas, criar a tela de game over e fazer o botão de recomeçar funcionar.

1
Ligue o dano às vidas

No Player.cs, no método TakeDamage() (que no Módulo 04 só fazia GD.Print), chame GameManager.Instance.LoseLife();. Agora cada dano custa uma vida de verdade.

2
Adicione Reset ao GameManager

Acrescente o método Reset() e a checagem de Lives <= 0 no LoseLife() (código da aba Conteúdo).

3
Crie a cena de Game Over

Nova cena com Control como raiz (GameOver). Adicione um Label "Game Over" centralizado e um Button "Tentar de novo". Salve em res://Scenes/UI/GameOver.tscn.

4
Ligue o botão

Anexe GameOver.cs à raiz. Conecte o signal pressed do Button ao método OnRetryPressed, que reseta e volta ao mapa_1.tscn.

5
Teste a derrota

Rode, tome dano até as vidas zerarem. O jogo deve pular para a tela de game over. Clique em "Tentar de novo": o nível recomeça com 3 vidas e placar zerado.

Ponto de verificação

O ciclo deve: (1) descontar vida a cada dano no HUD, (2) ir ao game over quando zerar, (3) recomeçar limpo ao clicar no botão — vidas e placar resetados via GameManager.Reset().

Condição de vitória com bandeira de fim Aula 5.2 · Area2D + cena de vitória
Difícil

Todo jogo precisa de um jeito de vencer. Adicione um objetivo ao fim do nível: uma bandeira que, ao ser tocada, leva à tela de vitória — reutilizando a Area2D do Módulo 04.

  • 1
    Crie uma cena Goal (Area2D + sprite de bandeira/placa + CollisionShape2D) e posicione no fim do mapa_1
  • 2
    No body_entered, confirme IsInGroup("player") e troque para res://Scenes/UI/Victory.tscn
  • 3
    Crie a cena Victory (igual à de game over: texto + botão "Jogar de novo")
  • 4
    O botão deve chamar GameManager.Reset() e voltar ao nível
  • 5
    Opcional: só permita vencer se o player tiver coletado todas as gemas (compare com um total no GameManager)

A Goal é conceitualmente idêntica à Gem: uma Area2D que reage ao body_entered. A diferença é o que ela faz — em vez de somar ponto, chama GetTree().ChangeSceneToFile(...).

Para "todas as gemas", guarde no GameManager quantas existem no nível (conte no início) e compare com o Score. Se faltar, ignore o toque na bandeira ou mostre um aviso.

Módulo 05 · Aula 5.3

Exportar para desktop

Transformar o projeto do editor num executável que roda sozinho — o passo que entrega o jogo para outras pessoas jogarem.

~25 minutos Editor + build

Do editor ao executável

Até agora o jogo só roda apertando F5 dentro do Godot. Para entregar a alguém, você precisa exportar: empacotar o projeto e o motor num programa que roda sem o editor. É o passo que transforma "meu projeto" em "meu jogo".

O que compõe uma build
1
Export template
Uma versão "sem editor" do motor Godot, específica para cada plataforma
2
Seu conteúdo (.pck)
Cenas, scripts e assets empacotados num arquivo de dados
3
Executável
O .exe (ou binário) que junta o motor ao seu .pck e roda o jogo

Export templates: o motor sem editor

Antes de exportar, o Godot precisa dos export templates — os binários do motor para cada sistema. Você baixa uma vez em Editor → Manage Export Templates → Download and Install. Eles precisam bater com a versão exata do seu Godot.

Versão do template = versão do editor

Templates da 4.6 não servem para um editor 4.7. Se a exportação reclamar de template ausente ou incompatível, quase sempre é isso: baixe os templates da versão idêntica à do seu editor.

Export presets: uma receita por plataforma

Em Project → Export você cria um preset por destino: Windows Desktop, Linux, macOS. Cada preset guarda as opções daquele alvo — caminho de saída, ícone, nome, arquitetura. Com um preset pronto, exportar vira um clique.

Projeto C# / .NET

Este curso usa Godot .NET (C#), então a exportação também compila o código C#. Use uma versão do Godot com suporte a .NET, tenha o .NET SDK instalado, e na primeira exportação o Godot faz o build do assembly junto. É normal a primeira build demorar mais.

Exportar de fato

Com o preset selecionado, Export Project gera o executável na pasta escolhida. O Godot cria o .exe e, ao lado, o .pck com seus dados (ou embute tudo, conforme a opção). Rodar o .exe abre o jogo em janela, sem editor, exatamente como o jogador vai ver.

Distribua a pasta inteira

Por padrão o jogo são dois arquivos: o .exe e o .pck com mesmo nome. Eles andam juntos — para enviar a alguém, zipe a pasta inteira, não só o .exe. (Dá para embutir o .pck no executável nas opções do preset, se preferir um arquivo só.)

Gerar o executável

Vamos exportar o jogo para Windows e rodá-lo fora do editor.

1
Instale os export templates

Menu Editor → Manage Export Templates → Download and Install. Aguarde o download (é grande). Confirme que a versão bate com o seu editor.

2
Confirme o .NET SDK

Como o projeto é C#, tenha o .NET SDK instalado (o mesmo que você configurou no Módulo 01). Sem ele, a exportação do assembly falha.

3
Crie o preset do Windows

Menu Project → Export → Add… → Windows Desktop. Se aparecer aviso sobre template, volte ao passo 1.

4
Defina a cena principal

Confirme em Project Settings → Application → Run → Main Scene que a cena inicial é o mapa_1.tscn (ou um menu). É ela que abre quando o jogo roda.

5
Exporte

Ainda em Export, clique em Export Project, escolha uma pasta vazia e um nome (ex.: MeuJogo.exe). A primeira build compila o C# e pode demorar.

6
Rode fora do editor

Abra a pasta e dê duplo clique no .exe. O jogo deve abrir em janela e funcionar como no editor — coletar gemas, HUD, game over, tudo.

Falhou a build do C#?

Se a exportação parar com erro de compilação, o problema está no código, não na exportação: confirme que o projeto roda por F5 sem erros no editor antes de exportar. Uma build limpa no editor é pré-requisito.

Ícone próprio e segunda plataforma Aula 5.3 · Presets e branding
Médio

Um .exe com o ícone padrão do Godot não parece um jogo seu. Dê identidade à build e prove que ela roda além do Windows.

  • 1
    Defina um ícone próprio do jogo em Project Settings → Application → Config → Icon
  • 2
    No preset do Windows, configure o ícone do executável e os campos de Product Name / Version
  • 3
    Adicione um segundo preset — Linux — e exporte também para ele
  • 4
    Confirme que os dois executáveis abrem o mesmo jogo (teste o Linux numa máquina/VM Linux se tiver acesso)

O ícone da janela (dentro do jogo) vem de Application → Config → Icon; o ícone do arquivo .exe no Windows é uma opção separada dentro do preset (campo Application → Icon do preset).

Um mesmo projeto gera quantos presets você quiser — o conteúdo é o mesmo .pck, só muda o binário do motor por plataforma. Não precisa duplicar nada do jogo.
