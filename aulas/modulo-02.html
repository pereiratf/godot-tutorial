Módulo 02 · Aula 2.1

CharacterBody2D e o sistema de física

Entender qual tipo de corpo físico usar e como o Godot gerencia movimento e colisão para personagens jogáveis.

~25 minutos Conceitual + código

O sistema de coordenadas 2D

Antes de mover qualquer coisa, é preciso entender como o Godot organiza o espaço. Quem aprendeu o plano cartesiano na matemática vai precisar ajustar uma intuição importante: o eixo Y é invertido.

Como a tela do Godot 2D é organizada
(0, 0)
+X → direita
+Y ↓ baixo
(175, 105)
−Y
+Y
−X
+X
Tela do jogo
Movimento horizontal
velocity.X = +200 → move para a direita velocity.X = -200 ← move para a esquerda
Movimento vertical
velocity.Y = +980 ↓ gravidade (cai) velocity.Y = -500 ↑ pulo (sobe)
Diferença em relação à matemática

No plano cartesiano da matemática, Y positivo aponta para cima e a origem fica no centro. Na tela do computador (e no Godot), a origem (0, 0) fica no canto superior esquerdo e Y positivo aponta para baixo — porque é assim que pixels são endereçados na memória de vídeo. Toda engine 2D segue essa convenção.

Qual tipo de corpo físico usar?

O Godot tem três tipos de corpo 2D para coisas que colidem. A escolha errada não quebra o jogo imediatamente — mas vai te criar bugs difíceis de diagnosticar mais tarde.

CharacterBody2D
  • Você move via
    Velocity + MoveAndSlide()
  • Colide mas não é empurrado pela física
  • Gravidade é manual — você escreve no código
  • Use para: personagem jogável, inimigos
RigidBody2D
  • Física simulada automaticamente
  • Você aplica forças, não posição direta
  • Gravidade, inércia, bounce são automáticos
  • Use para: caixas, projéteis, objetos físicos
StaticBody2D
  • Não se move — só colide
  • Mais eficiente que os outros dois
  • Pode ter fricção e material físico
  • Use para: chão, paredes, plataformas
Por que não usar RigidBody2D para o player?

Com RigidBody2D você perde controle direto da posição. A física acumula forças — um pulo acaba sendo o resultado de impulsos, fricção e gravidade interagindo. Conseguir um "game feel" preciso (pulo responsivo, cancelamento de pulo, dash) fica muito mais difícil. CharacterBody2D te dá controle total a custo de implementar a gravidade você mesmo — o que é simples e vale a pena.

MoveAndSlide() — o motor do movimento

O MoveAndSlide() é o método que faz o CharacterBody2D se mover respeitando colisões. Ele não recebe parâmetros — lê a propriedade Velocity do próprio body, tenta mover essa distância, e se encontrar um colisor no caminho, desliza ao longo da superfície em vez de parar abruptamente.

Player.cs — uso mínimo C# 
private Vector2 _velocity;

public override void _PhysicsProcess(double delta)
{
    _velocity = Velocity;  // relê o estado que o MoveAndSlide resolveu

    // ... modifica _velocity ...

    Velocity = _velocity;  // grava de volta
    MoveAndSlide();       // move o body e resolve colisões
}
Por que reler Velocity todo frame

A linha _velocity = Velocity; no topo não é opcional: o MoveAndSlide() reescreve a propriedade Velocity ao resolver colisões (zera o Y ao pousar, o X ao bater na parede). Reler garante que você continua do estado real resolvido. Se tratar _velocity como fonte única e parar de reler, o valor da queda fica "preso" e o personagem despenca em velocidade máxima ao sair de uma borda.

Após chamar MoveAndSlide(), você pode consultar o estado da colisão com três métodos:

Métodos de estado pós-movimento
IsOnFloor()
O body está em contato com uma superfície abaixo. Use para detectar se pode pular.
IsOnWall()
O body bateu numa parede lateral. Útil para wall jump e escalada.
IsOnCeiling()
O body colidiu com uma superfície acima. Cancelar velocidade Y evita "grudar" no teto.

Gravidade manual — por que é assim?

O CharacterBody2D não tem gravidade automática. Isso é uma escolha de design do Godot: ele não quer assumir nada sobre o seu jogo. Você adiciona gravidade incrementando Velocity.Y a cada frame de física:

Player.cs — com gravidade C# 
public partial class Player : CharacterBody2D
{
    [Export] public float Gravity = 980f; // pixels/segundo²

    private Vector2 _velocity;

    public override void _PhysicsProcess(double delta)
    {
        _velocity = Velocity;

        // Aplica gravidade somente quando no ar
        if (!IsOnFloor())
            _velocity.Y += Gravity * (float)delta;

        Velocity = _velocity;
        MoveAndSlide();
    }
}

O loop de física do personagem

Em cada frame de física, o código do personagem segue sempre a mesma sequência:

Sequência em _PhysicsProcess a cada frame
1
Lê input
Input.GetAxis(), Input.IsActionJustPressed()
2
Aplica gravidade
_velocity.Y += Gravity * delta se não estiver no chão
3
Calcula velocidade
Define _velocity.X pelo input; aplica pulo se condições OK
4
MoveAndSlide()
Move o body, resolve colisões, atualiza IsOnFloor()

Essa sequência importa: IsOnFloor() só retorna o valor correto depois que MoveAndSlide() rodou. Detectar pulo antes de mover pode dar resultados incorretos em bordas de plataforma.

Personagem que cai

Antes de adicionar controles, vamos ver o personagem respondendo à gravidade. A cena já está pronta no projeto base — o foco aqui é escrever o primeiro script de física.

Projeto base deste módulo

Baixe e abra o projeto base antes de continuar. Ele contém a cena player.tscn (CharacterBody2D + AnimatedSprite2D + CollisionShape2D, sem script) e a cena mapa_1.tscn com chão e plataformas para testes. Animações e TileMapLayer serão abordados num módulo futuro.

⬇ Baixar projeto base
1
Abra o projeto no Godot

Extraia o zip, abra o Godot e importe a pasta. Confirme que as cenas Scenes/Player/player.tscn e Scenes/World/mapa_1.tscn aparecem no FileSystem. Abra mapa_1.tscn e pressione F5 — o personagem deve aparecer parado no ar, sem cair (sem script ainda).

2
Crie o script de gravidade

Abra Player.tscn. Selecione o node raiz Player → ícone de script → Criar. Godot gera Player.cs automaticamente. Cole o código abaixo.

Player.cs C# 
using Godot;

public partial class Player : CharacterBody2D
{
    [Export] public float Gravity = 980f;

    private Vector2 _velocity;

    public override void _PhysicsProcess(double delta)
    {
        _velocity = Velocity;

        if (!IsOnFloor())
            _velocity.Y += Gravity * (float)delta;

        Velocity = _velocity;
        MoveAndSlide();
    }
}

O personagem deve cair e parar exatamente no chão. Experimente mudar o valor de Gravity no Inspector (sem recompilar) e pressione F5 novamente para ver a diferença no feel.

O que observar

Com Gravity = 980 o personagem cai em velocidade realista (~1 segundo para 490px). Valores maiores como 2000 dão um feel mais "arcade" — mais peso, queda rápida. Muitos jogos de plataforma usam gravidade 2–3× a real propositalmente.

Respawn ao cair no vazio Aula 2.1 · Física
Médio

Em jogos de plataforma, cair num buraco "mata" o personagem e o devolve a um ponto seguro. Você vai implementar esse respawn usando só o que viu nesta aula: posição, velocidade e a noção de eixo Y.

A ideia: guardar um ponto de respawn e, a cada frame, checar se o personagem caiu longe demais. Atenção ao eixo Y — como ele cresce para baixo, "caiu demais" significa Position.Y maior que um limite (não menor, como o instinto da matemática sugere).

Para testar agora — antes de termos movimento horizontal — arraste o Player no editor para um ponto sem chão embaixo (além da borda do cenário) e rode: ele cai, ultrapassa o limite e reaparece no SpawnPoint, parado.

  • 1
    Declare [Export] Vector2 SpawnPoint = new Vector2(192, 192) e [Export] float FallLimit = 600f
  • 2
    Após o MoveAndSlide(), cheque se Position.Y > FallLimit
  • 3
    Se verdadeiro, faça Position = SpawnPoint e Velocity = Vector2.Zero
  • 4
    Teste: posicione o Player sobre um vazio — ele deve cair, sumir e reaparecer no SpawnPoint

O sinal da comparação é o que mais confunde: Y cresce para baixo, então quem despencou tem Position.Y grande. Use >, não <.

Zerar Velocity no respawn evita que o personagem reapareça já "despencando" com a velocidade acumulada da queda.

if (Position.Y > FallLimit) { Position = SpawnPoint; Velocity = Vector2.Zero; }

Módulo 02 · Aula 2.2

Input: ações, não teclas

Como o sistema de InputMap do Godot desacopla controles do código — e por que isso importa desde o começo.

~20 minutos Editor + código

Por que mapear ações, não teclas?

A abordagem mais óbvia seria checar teclas diretamente no código:

Player.cs — abordagem frágil C# 
// Frágil: amarrado ao teclado, não remapeável, não funciona com gamepad
if (Input.IsKeyPressed(Key.Space))
    _velocity.Y = -JumpForce;

O problema: esse código conhece a implementação física do controle (a tecla Space). Se o jogador quiser remapear para gamepad, ou se você quiser suporte a controle sem mexer no código, não tem como. O InputMap resolve isso: você define ações com nomes semânticos, mapeia dispositivos para elas no editor, e o código só conhece o nome da ação.

Tecla direta — problemas
  • Não remapeável pelo jogador
  • Cada plataforma/dispositivo exige código diferente
  • Teclado e gamepad precisam de condicionais separadas
  • Nomes de teclas mudam entre layouts (QWERTY / AZERTY)
InputMap — vantagens
  • Teclado, gamepad e touch mapeados para a mesma ação
  • Jogador pode remapear sem alterar código
  • Código lê "jump" — não importa o dispositivo
  • Você adiciona suporte a gamepad sem tocar no script

Configurando o InputMap

Acesse Projeto → Configurações do Projeto → Mapa de Entrada. O Godot já tem ações padrão como ui_left, ui_right, ui_accept — úteis para menus. Para o jogo, crie ações próprias com nomes claros:

Ações a criar para o player
move_left
Tecla A ou seta esquerda — movimento horizontal esquerdo
move_right
Tecla D ou seta direita — movimento horizontal direito
jump
Tecla Space ou W ou seta cima — pulo

Para cada ação: clique em Adicionar Ação, digite o nome, pressione Enter. Depois clique no + ao lado da ação para adicionar eventos (teclas, botões de gamepad).

Os três métodos de Input

O Input singleton tem três métodos principais, e a escolha errada cria bugs sutis:

GetAxis()
  • Retorna -1.0 a 1.0
  • Combina dois ações opostas
  • Suporta valores intermediários (gamepad analógico)
  • Use para: movimento contínuo
IsActionJustPressed()
  • true somente no frame em que foi pressionado
  • Volta para false no frame seguinte
  • Não acumula enquanto mantido
  • Use para: pulo, ataque, interação
IsActionPressed()
  • true em todos os frames que a ação está ativa
  • Continua true enquanto mantido
  • Não detecta o momento exato do press
  • Use para: carga de poder, disparo automático
Erro clássico: pulo com IsActionPressed

Se você usar IsActionPressed("jump") para pular, o personagem pula repetidamente enquanto a tecla é mantida — uma vez por frame de física (60x/segundo). IsActionJustPressed garante que o pulo acontece apenas uma vez por pressão, mesmo que o jogador segure a tecla.

Configurar o InputMap e ler movimento

Antes de implementar o personagem completo, vamos criar as ações e confirmar que o input está sendo lido corretamente.

1
Crie as ações no InputMap

Projeto → Configurações do Projeto → Mapa de Entrada. Adicione as ações move_left, move_right e jump. Para cada uma, adicione pelo menos uma tecla: A/D/Space ou as setas.

2
Leia o eixo horizontal e imprima

Temporariamente, substitua o conteúdo do _PhysicsProcess pelo código abaixo. Execute o jogo e pressione as teclas para ver os valores no Output.

Player.cs — diagnóstico de input C# 
public override void _PhysicsProcess(double delta)
{
    float direction = Input.GetAxis("move_left", "move_right");
    GD.Print($"Direção: {direction}");

    if (Input.IsActionJustPressed("jump"))
        GD.Print("Pulo! (JustPressed)");

    if (Input.IsActionPressed("jump"))
        GD.Print("Jump mantido (Pressed)");
}
O que observar no Output

Segure a tecla de pulo por 2 segundos. Você vai ver "Pulo! (JustPressed)" aparecer apenas uma vez (no primeiro frame), enquanto "Jump mantido (Pressed)" aparece em todos os frames enquanto a tecla está pressionada. Essa é a diferença crucial para implementar pulo corretamente.

Dash horizontal Aula 2.2 · Input
Médio

Implemente um dash: quando o jogador pressiona shift (crie a ação dash no InputMap), o personagem recebe um impulso horizontal na direção em que está se movendo, com velocidade 3× maior por 0.15 segundos.

  • 1
    Adicione a ação dash no InputMap (Shift esquerdo)
  • 2
    No script, declare private float _dashTimer = 0f
  • 3
    Quando IsActionJustPressed("dash"), atribua _dashTimer = 0.15f
  • 4
    Em cada frame, decremente o timer e aplique velocidade triplicada enquanto ele for maior que zero

Use _dashTimer -= (float)delta em cada frame. A velocidade horizontal fica: _velocity.X = direction * Speed * (_dashTimer > 0 ? 3f : 1f).

Guarde a direção no momento do dash para que ele continue na mesma direção mesmo se o jogador soltar a tecla.

Wall jump com GetWallNormal() Aula 2.2 · Física + Input
Difícil

O wall jump é uma mecânica clássica de plataforma: o personagem pode pular enquanto está em contato com uma parede, sendo lançado na direção oposta. A chave é saber de que lado está a parede — e para isso usamos GetWallNormal().

Como funciona a normal da parede

Uma normal é um vetor perpendicular a uma superfície, apontando para fora dela. GetWallNormal() retorna esse vetor apontando em direção ao player. Parede à direita → normal aponta para a esquerda (Normal.X = -1). Parede à esquerda → normal aponta para a direita (Normal.X = +1). O Normal.X já indica a direção exata em que o player deve ser lançado para se afastar da parede.

  • 1
    Declare [Export] public float WallJumpForce = 350f no script
  • 2
    Adicione a condição: IsOnWall() && !IsOnFloor() && IsActionJustPressed("jump")
  • 3
    Dentro dessa condição, leia GetWallNormal() e use o eixo X como direção horizontal do pulo
  • 4
    Aplique _velocity.Y = -JumpForce e _velocity.X = GetWallNormal().X * WallJumpForce
  • 5
    Adicione duas paredes verticais (StaticBody2D) na cena e confirme que o player ricocheteia corretamente em ambos os lados

A normal já aponta na direção certa — não precisa inverter. Se o player está encostado na parede direita (Normal.X = -1), multiplicar por WallJumpForce dá velocidade negativa (para a esquerda), que é exatamente o que queremos.

if (IsOnWall() && !IsOnFloor() && Input.IsActionJustPressed("jump"))
{
    var n = GetWallNormal();
    _velocity.Y = -JumpForce;
    _velocity.X = n.X * WallJumpForce;
}

Módulo 02 · Aula 2.3

O personagem completo

Juntar gravidade, input e pulo num script coeso — e ajustar o feel até ficar responsivo.

~35 minutos Código + editor

O script completo

Com CharacterBody2D, gravidade manual e InputMap configurados, o script do personagem jogável é direto:

Player.cs C# 
using Godot;

public partial class Player : CharacterBody2D
{
    [Export] public float Speed      = 200f;
    [Export] public float JumpForce  = 500f;
    [Export] public float Gravity    = 1200f;

    private AnimatedSprite2D _sprite;
    private Vector2 _velocity;

    public override void _Ready()
    {
        _sprite = GetNode<AnimatedSprite2D>("AnimatedSprite2D");
    }

    public override void _PhysicsProcess(double delta)
    {
        _velocity = Velocity;

        // 1. Gravidade
        if (!IsOnFloor())
            _velocity.Y += Gravity * (float)delta;

        // 2. Movimento horizontal
        float direction = Input.GetAxis("move_left", "move_right");
        _velocity.X = direction * Speed;

        // 3. Pulo
        if (Input.IsActionJustPressed("jump") && IsOnFloor())
            _velocity.Y = -JumpForce;

        // 4. Cancelar pulo no teto
        if (IsOnCeiling())
            _velocity.Y = 0;

        Velocity = _velocity;
        MoveAndSlide();
        UpdateAnimations(direction);
    }

    private void UpdateAnimations(float direction)
    {
        if (direction != 0)
            _sprite.FlipH = direction < 0;
    }
}

UpdateAnimations — centralizando o visual

Em vez de colocar lógica de sprite diretamente em _PhysicsProcess, o script usa um método dedicado UpdateAnimations. O _PhysicsProcess só chama o método ao final, passando a direção como parâmetro — tudo que é visual fica isolado num único lugar.

Player.cs — UpdateAnimations C# 
private void UpdateAnimations(float direction)
{
    if (direction != 0)
        _sprite.FlipH = direction < 0; // true = virado para esquerda
}
Por que separar num método?

No módulo "Dar vida ao jogo", este método vai crescer: _sprite.Play("run") quando em movimento, _sprite.Play("jump") no ar, _sprite.Play("idle") parado. Centralizar aqui desde já garante que _PhysicsProcess não acumule lógica visual — cada método tem uma responsabilidade clara.

Ajustando o feel

Os valores de Speed, JumpForce e Gravity são [Export] propositalmente — você pode ajustá-los no Inspector enquanto o jogo roda no editor (F5 com a cena aberta) para encontrar o feel certo sem recompilar. Valores de referência para plataforma arcade:

Valores de partida para plataforma 2D
Speed
180–250 px/s · Rápido demais = difícil de controlar; devagar demais = pesado
JumpForce
400–600 px/s · Quanto maior, mais alto o pulo relativo à gravidade
Gravity
900–1400 px/s² · Gravidade alta = pulo mais "arcade" (sobe rápido, cai rápido)
O ratio que define o feel

O que o jogador sente não é o valor absoluto de JumpForce, mas a relação JumpForce / Gravity. Dobrar os dois mantém o mesmo arco de pulo mas com tudo acontecendo mais rápido — jogo mais responsivo. Diminuir a razão dá pulos mais altos e flutuantes; aumentar dá pulos curtos e precisos.

Implementar e ajustar o personagem

Substitua o script da Aula 2.1 pelo script completo e itere nos valores até o movimento parecer bom.

1

2

Ponto de verificação

O personagem deve: (1) cair com gravidade ao ser solto no ar, (2) mover horizontalmente com A/D, (3) pular com Space apenas quando no chão, (4) não pular ao segurar Space, (5) parar de subir se bater no teto, (6) virar o sprite ao mudar de direção.

Animações no UpdateAnimations Aula 2.3 · AnimatedSprite2D
Médio

O projeto base já tem as animações "idle", "run", "jump" e "fall" configuradas no AnimatedSprite2D. Expanda o método UpdateAnimations para chamar _sprite.Play() com a animação correta de acordo com o estado do personagem.

  • 1
    Quando !IsOnFloor() e Velocity.Y < 0, reproduza "jump"
  • 2
    Quando !IsOnFloor() e Velocity.Y >= 0, reproduza "fall"
  • 3
    Quando IsOnFloor() e direction != 0, reproduza "run"
  • 4
    Quando IsOnFloor() e direction == 0, reproduza "idle"
  • 5
    Teste: caminhe até a borda de uma plataforma e caia — o sprite deve mudar de "run" para "fall" imediatamente

A ordem dos if/else importa: cheque o estado aéreo primeiro (!IsOnFloor()), depois o estado no chão. Se você checar direction != 0 antes, um personagem correndo para fora de uma borda vai mostrar "run" em vez de "fall" no primeiro frame.

private void UpdateAnimations(float direction)
{
    if (direction != 0)
        _sprite.FlipH = direction < 0;

    if (!IsOnFloor())
        _sprite.Play(Velocity.Y < 0 ? "jump" : "fall");
    else if (direction != 0)
        _sprite.Play("run");
    else
        _sprite.Play("idle");
}
Coyote Time Aula 2.3 · Game feel
Difícil

Coyote time é uma técnica clássica de plataforma: o jogador pode pular por alguns frames após sair de uma plataforma, não apenas enquanto ainda está nela. Isso torna o controle mais perdoador sem afetar o comportamento percebido.

  • 1
    Declare private float _coyoteTimer = 0f e private const float CoyoteTime = 0.12f
  • 2
    Quando IsOnFloor() for verdadeiro, redefina o timer: _coyoteTimer = CoyoteTime
  • 3
    Quando IsOnFloor() for falso, decremente: _coyoteTimer -= (float)delta
  • 4
    A condição de pulo passa de IsOnFloor() para _coyoteTimer > 0f
  • 5
    Após pular, zere o timer para evitar segundo pulo no ar

O timer deve ser decrementado independente de IsOnFloor(). Quando no chão, você recarrega para CoyoteTime; quando no ar, ele conta regressivamente. O Mathf.Max(0, _coyoteTimer - delta) evita valores negativos.

Lembre de zerar o timer imediatamente após o pulo com _coyoteTimer = 0 — senão o jogador poderia pular duas vezes (uma com coyote, outra porque o timer ainda está positivo).
